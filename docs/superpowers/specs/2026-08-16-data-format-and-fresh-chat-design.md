# Заморозка формата данных и разговор с чистого листа

Дата: 16.08.2026. Версия на момент замысла: 0.9.0.

Два дела одним заходом.

1. **Формат данных** — пункт из разбора «что нужно для 1.0.0»: после 1.0 ломать
   `data.json` и `history.json` нельзя, а номера версии в них нет вообще.
2. **Разговор с чистого листа по горячей клавише** — просьба Льва: запуск из
   заметки не должен тащить за собой прежнюю беседу, чтобы за неё не платить.

---

## Часть 1. Формат данных

### Что не так сегодня

`loadStore()` (`main.ts:373`) читает `data.json` через `loadData()` и валит два
разных случая в один:

```ts
const raw = (await this.loadData()) as Partial<StoredData> | null;
this.settings = mergeSettings(raw?.settings ?? raw);
```

`loadData()` — это `readJson` Obsidian, проверено по `obsidian.asar` 1.13.7:

```js
try { return JSON.parse(await adapter.read(path)) }
catch (e) { if (e.code === "ENOENT") return null;
            console.error("failed to read JSON", ...); }   // → undefined
```

То есть **файла нет → `null`, файл битый → `undefined`**, и плагин от битого
файла не падает. Различить эти случаи можно, ничего не перечитывая своими
руками. Сейчас оба дают умолчания, а первое же сохранение настроек пишет
умолчания поверх файла. В `settings.profiles` лежат ключи API всех
провайдеров — значит один битый файл молча стирает их все.

У `history.json` то же самое (`main.ts:352`: `catch { return [] }`), но там
всего лишь лента.

Ещё две дыры помельче:

- **Незнакомые поля верхнего уровня теряются.** Внутри настроек их бережёт
  `{ ...base, ...s }` в `mergeSettings`, а вот верхний уровень файла пишется
  как `saveData({ settings })` — всё, чего мы не знаем, стирается.
- **Лента читается вслепую**: `raw as HistoryItem[]` доверяет любому массиву,
  и элемент-`null` внутри уронит отрисовку панели.

### Устройство

Разбор переезжает в новый **`src/store.ts`** — чистые функции, ни одного
импорта из `obsidian`. Тогда тестовый харнесс собирает его как остальные
модули, и проверки на битые файлы пишутся напрямую. `main.ts` остаётся
хозяином диска: прочитал байты — отдал разбирать.

```ts
export const SCHEMA = 1;

export type StoreState = "fresh" | "ok" | "ahead" | "broken";

export interface StoreRead {
  settings: AiAssistSettings;
  /** Лента из data.json прежних версий — её переносят в history.json. */
  legacy?: HistoryItem[];
  /** Всё прочее с верхнего уровня файла: записывается обратно нетронутым. */
  rest: Record<string, unknown>;
  state: StoreState;
}

export function readStore(raw: unknown): StoreRead;
export function writeStore(settings: AiAssistSettings, rest: Record<string, unknown>): StoredData;

export interface HistoryRead {
  items: HistoryItem[];
  broken: boolean;
}

export function readHistory(raw: unknown): HistoryRead;
export function writeHistoryFile(items: HistoryItem[]): StoredHistory;
```

`StoredHistory` — новый тип рядом со `StoredData` в `types.ts`:
`{ schemaVersion: number; items: HistoryItem[] }`. В `StoredData` добавляется
`schemaVersion?: number` (необязательное: файл версии 0 его не имеет).

`readStore` разбирает так:

| что пришло | state | что делаем |
|---|---|---|
| `null` | `fresh` | умолчания, молчим — первая установка |
| `undefined` | `broken` | копия + умолчания + сказать вслух |
| не объект (число, строка, массив) | `broken` | то же |
| объект с `settings` | `ok` / `ahead` | `ahead`, если `schemaVersion > SCHEMA` |
| объект без `settings` | `ok` | древний формат, где настройки лежали в корне — сохраняем нынешнее поведение `raw?.settings ?? raw` |

В случае «настройки в корне» `rest` пустой: иначе настройки продублировались бы
на верхнем уровне файла.

`writeStore` пишет `{ ...rest, schemaVersion: SCHEMA, settings }`. Поле
`history` при переносе ленты в свой файл из `rest` выбрасывается, как и сейчас.

`readHistory` понимает и голый массив (версия 0), и `{ schemaVersion, items }`;
элементы, не являющиеся объектами, отсеиваются. Всё остальное — `broken: true`
и пустая лента.

### Битый файл

Порядок в `main.ts`:

1. `readStore` вернул `broken`.
2. Сырой текст файла читаем сами (`vault.adapter.read`) — `loadData` отдаёт
   только разобранное — и кладём рядом в `data.json.bak`.
3. **Если `.bak` уже есть — не трогаем.** Старая копия ценнее: в ней настоящие
   ключи, а сегодняшний битый файл мог быть уже огрызком.
4. Уведомление: что случилось и где копия.

`data.json.bak` не проходит `isPluginFile` в Obsidian (там только
`manifest.json`, `main.js`, `styles.css`, `data.json`) — значит синхра копию не
увезёт, она останется на этой машине.

Для `history.json` копия делается так же, но **молча**: лента расходная, пугать
человека на старте из-за неё незачем.

### Файл из будущего

`schemaVersion` больше нашего — читаем как умеем и молчим. Незнакомые поля
проносим через сохранение: внутри настроек это уже делает `{ ...base, ...s }`,
на верхнем уровне — новый `rest`. Тест закрепляет оба.

Так вторая машина, ушедшая вперёд, ничего не теряет.

### Не затоптать чужое: `onExternalSettingsChange`

Хук у Obsidian есть, у плагина его нет — проверено по `obsidian.asar`:
`onRaw` ловит запись в `data.json` плагина, зовёт `_onConfigFileChange`, а тот
вызывает `onExternalSettingsChange()`, **только если плагин его определил**, и
предварительно сверяет mtime файла с прошлым чтением.

Без хука картина такая: синхра привозит `data.json` со второй машины, плагин
держит в памяти своё старое, и ближайшее сохранение кладёт старое поверх
нового. Взводится оно на каждую букву черновика (`saveSettingsSoon`, 1 с).

Что делаем:

- Перечитываем **только настройки**, не ленту. `loadStore` целиком звать
  нельзя: при включённом `freshStart` он чистит историю, и привезённые
  настройки снесли бы живой разговор.
- Ленту трогать и не нужно: `history.json` не проходит `isPluginFile`, то есть
  Obsidian Sync его вообще не возит.
- Правило разрешения споров: **чужой файл побеждает** — Obsidian уже сверил
  mtime, он новее. Исключение одно: `draft`, черновик поля ввода. Он про эту
  машину и эту секунду.
- Взведённый таймер записи настроек гасим, не сбрасывая на диск: иначе
  затопчем только что прочитанное.
- После чтения: перерегистрировать команды действий, освежить шапку панели,
  перерисовать вкладку настроек, если она открыта.

### Описание формата

Новый файл `docs/data-format.md`: что за файлы, что в них лежит, правило
совместимости (номер версии, поля, которых мы не знаем, беречь; в мажорной
версии формат не ломать). README на 18 КБ — ему туда не надо.

## Часть 2. Разговор с чистого листа по горячей клавише

### Что не так сегодня

Сам запрос по хоткею прошлое **уже не тащит**: `runAction` ставит `fresh: true`
(`main.ts:648`) для действий в режиме «показать в панели», разовый промпт идёт
тем же путём, а правка `replace`/`append` в панель не заходит вовсе.

Токены копятся дальше: ответ от хоткея ложится в ленту, и следующий вопрос,
набранный в самой панели, тащит уже всё накопленное — до 24 000 знаков
(`CONTEXT_BUDGET`). Тот же путь у «спросить о выделенном»: он только вешает
фрагмент на плашку, а вопрос уходит со всей лентой.

### Поведение

Запуск из заметки начинает разговор заново — лента чистится, как кнопкой
«Новый чат». Чистят те входы, что **пишут в панель**:

- действие в режиме «показать в панели» (`runAction`, `action.mode === "chat"`);
- разовый промпт из быстрого меню по Enter (идёт через тот же `runAction`);
- «спросить о выделенном» (`askAboutSelection`).

Правка текста в заметке (`replace`/`append`) разговор не трогает: она в панель
ничего и не кладёт, кроме карточки журнала.

Два правила поверх:

- **Записи журнала правок остаются на местах.** В их карточках живёт кнопка
  «Отменить правку», и стереть их значит отобрать возврат. Правило в плагине
  уже принято — так работает обрезка ленты кнопками под сообщениями
  (`view.ts:691`, `cut`).
- **Стёртое возвращается нажатием по уведомлению** — общий приём `snapshot()`
  (`view.ts:671`), тот же, что у «нового чата» и правки ленты.

Плашка не трогается: фрагмент вешает сам вызывающий, а картинки на ней — не
разговор.

Если чистить нечего (в ленте одни записи журнала или она пуста) — молчим, без
уведомления. Если панель занята живым запросом — не чистим: ответ пришёл бы в
пустую ленту и повис без вопроса.

### Настройка

`freshOnAction: boolean`, по умолчанию `true`. В настройках рядом с
«Открывать Obsidian с пустой лентой» (`setFresh`, `settings.ts:544`) — они
родственны. Выключенное значение возвращает нынешнее поведение.

Умолчание достаётся и тем, кто обновляется: иначе Лев не получит просимого без
похода в настройки, а экономия эта нужна всем. Это **смена поведения против
выпущенной 0.9.0** — как было со сменой Enter/Ctrl+Enter, её место первым
разделом в заметках к релизу.

### Устройство

В `view.ts` — новый метод, собранный из уже существующих кусков:

```ts
/**
 * Разговор с чистого листа перед запуском из заметки. Записи журнала правок
 * остаются: в их карточках живёт кнопка «Отменить правку».
 */
freshTalk(): void {
  if (!this.host.settings.freshOnAction) return;
  // Живой запрос: его ответ пришёл бы в пустую ленту и повис без вопроса.
  if (this.controller) return;
  if (dropTalk(this.host.history).length === this.host.history.length) return;
  const undo = this.snapshot();
  this.cut(0, this.host.history.length);
  undo(t("chatFreshStarted"));
}
```

`cut` уже оставляет `ActionEntry`, гасит вложения через `forgetSaved`, пишет
ленту и перерисовывает панель — своего кода почти не появляется.

Отбор выносится чистой функцией **`dropTalk(history)`** в `history.ts`
(там же, где `contextWindow`) — чтобы правило «журнал остаётся» проверялось
тестом, а не глазами. Это заодно первый шаг к третьему пункту списка 1.0:
тесты туда, где живут баги.

Звонки: в `runAction` (ветка `mode === "chat"`) и в `askAboutSelection` —
сразу после `await this.openChat()`, до `submit` и `takeSelection`.

Новые ключи i18n (оба языка): `setFreshAction`, `setFreshActionDesc`,
`chatFreshStarted`.

## Часть 3. Промпт: знаки не подменять

Просьба Льва: модель не должна ставить в его текст длинное тире вместо дефиса и
типографские пробелы вместо обычных — «иишные» знаки видно за версту, а
неразрывный пробел вдобавок ломает поиск по заметкам.

Фраза дописывается в **`promptKeepMarkup`**, а не в промпт орфографии, по двум
причинам:

- знаки модель подменяет одинаково в «сократить», «улучшить» и «расширить», а
  не только в орфографии;
- `promptKeepMarkup` живёт в `i18n.ts` и потому **доезжает до всех сам**, тогда
  как промпт действия лежит в `data.json`, и правку пришлось бы дописывать в
  `LEGACY_PROMPTS` (иначе установленный плагин её не увидит).

Правило формулируется симметрично — «какой знак пришёл, такой и верни», — чтобы
не спорить с самим действием: орфография обязана править пунктуацию, и запрет
касается подмены начертания знака, а не расстановки знаков.

Оба языка:

```
Сами знаки не подменяй: дефис не превращай в длинное тире, а обычный
пробел — в неразрывный или узкий; какой знак пришёл, такой и верни.

Do not swap the characters themselves: a hyphen must not become an em dash
and a plain space must not become a non-breaking or thin one — return the
same character that came in.
```

**Проверить вживую до релиза.** Прошлая правка `promptKeepMarkup` уехала в
0.9.0 непроверенной: LM Studio закрылась до прогона, а Ollama на 12B не
уложилась в 300 с. Здесь проверка дешёвая — прогнать правку по куску с
дефисами и посмотреть на знаки в ответе.

## Тесты

Новые проверки в `tools/test-parse.mjs`, модуль `src/store.ts` подключается как
остальные.

**Разбор `data.json`:**

- `null` → `fresh`, умолчания;
- `undefined` → `broken`;
- строка, число, массив → `broken`;
- `{}` → `ok`, умолчания;
- `{ settings: {...} }` без `schemaVersion` → `ok` (версия 0);
- `{ schemaVersion: 1, settings }` → `ok`;
- `{ schemaVersion: 99, settings }` → `ahead`;
- настройки в корне (древний формат) → `ok`, `rest` пустой;
- незнакомое поле верхнего уровня переживает круг `readStore` → `writeStore`;
- незнакомое поле внутри `settings` переживает тот же круг.

**Разбор `history.json`:**

- голый массив → те же записи;
- `{ schemaVersion: 1, items }` → те же записи;
- объект без `items`, строка, `null` → пусто и `broken`;
- мусор внутри массива (`null`, число, строка) отсеивается, живые записи
  остаются.

**`dropTalk`:**

- разговор с записями журнала вперемешку → остаются только записи журнала, в
  прежнем порядке;
- лента из одних записей журнала → не меняется (значит и чистить нечего).

## Что НЕ делаем

- Не трогаем `view.ts` крупно: вынос машины состояний «чей сейчас запрос» —
  отдельный заход, третий пункт списка 1.0.
- Не заводим миграций между версиями формата: `SCHEMA` заводится равным 1, а
  прошлые файлы читаются как версия 0 тем же кодом, что и сейчас. Механизм
  миграций появится, когда появится что мигрировать.
- Не режем `history.json` по размеру и не заводим архив разговоров — это
  отдельная отложенная идея.

## Версия

0.10.0: новая настройка и смена поведения. 1.0.0 — решение Льва, и до неё
остаются мобильный проход по вложениям и «отлежаться».
